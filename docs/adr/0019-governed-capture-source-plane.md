# ADR 0019: governed capture source plane

- Status: proposed for K4-1 review
- Date: 2026-09-28
- Depends on: ADR 0004 and the Home/Personal Agent capture design. ADR 0018 is the separately approved device-principal predecessor; it is not in this `outcome-loop` tree and is not copied or renumbered here.

## Decision

K4-1 adds only daemon-owned SQLite metadata for `CaptureGrant`, `SourceArtifact`, and `SourceSegment`. Screen frames and Accessibility trees have independent grant rows, independent OS permission identities (`screen_recording` and `accessibility`), and independent permission states. Audio has a reserved schema discriminator but no K4-1 write path or collector. No single global capture permission exists. A grant is explicit, visible through its stored state, owner- and device-bound, purpose-bound, and revocable. A granted OS permission does not create owner consent, and consent for one modality does not authorize another.

The grant carries bounded JSON for included/excluded app, person and space identifiers and time windows. The Go domain validates entry length, count, duplicates and window ordering; SQLite validates a bounded JSON object. This preserves one portable grant identity while allowing later policy vocabulary versions without adding a column for every filter. `allowed_space_ids_json` is a separately validated bounded list of destination `ResponsibilitySpace` IDs. The current shared space model only materializes `WorkProject`, so K4-1 records portable IDs without claiming that Home spaces or cross-owner space validation already exist. A later authenticated service must resolve and authorize those IDs before any destination use.

Grant state is `active`, `paused`, `denied`, `stale`, `failed`, `revoked` or `deleted`. Only `active` with a granted, modality-matched OS permission can persist or expose ordinary source records. Every policy change, including exclusions, pause and revocation, is a compare-and-swap that increments `policy_generation` once. `deleted` is reserved for a later cleanup worker: the K4-1 store refuses to mark a grant deleted because it cannot yet prove raw and derived custody removal. Revoked grants cannot be reactivated. The OS permission observation is separate from consent state and must be revalidated by the later platform adapter. The stored `processing_route` is constrained to `local`; provider processing is not available. Disclosure, raw/derived retention, sensitivity, bystander, owner export and deletion behavior are explicit fields rather than implied defaults.

Artifact and segment IDs are portable, owner-scoped IDs, never SQLite row IDs. Artifacts reference owner, grant, captured generation and modality with a composite foreign key. Segments reference the exact artifact lineage with a second composite key; an ordinal and either a time interval or an offset interval locate a part without assuming an image, OCR text or recording. The artifact's lowercase SHA-256 hash addresses the exact source bytes committed to local custody. The blob reference is an opaque `local:` handle, not a path, provider URL or bytes stored in SQLite. It is unique globally; `(owner, grant, generation, algorithm, hash)` is unique within one policy generation, while identical bytes may appear under independently governed grants or a later generation. The future blob custodian must verify the hash on write/read and securely handle any staged blob rejected at the metadata fence. `SourceArtifact` and `SourceSegment` remain untrusted source material, not admitted Memory, Open Loop, Outcome, or execution authority.

## Final persistence and revocation fence

Kennel's existing SQLite store has one writer connection and a `writeMu`; SQLite itself serializes writes across connections and processes. The K4-1 artifact and segment inserts are single conditional `INSERT ... SELECT` statements that recheck the current grant state, OS permission, owner, modality and policy generation at their final SQL write. Segment insertion also checks artifact lineage and availability. Policy update is a generation CAS on that writer. An acknowledged policy change means its SQL update committed after any prior source insert on the writer; later inserts with the old generation affect zero rows and return `ErrCaptureStaleGrant`. Ordinary source reads also join the current active grant and generation, so a pause, exclusion change or revoke hides old custody references immediately. This is the durable metadata primitive implemented in K4-1.

A later collector must carry the observed generation through capture, local staging, derivation and every final persistence attempt; discard staged blobs and derivatives on stale or denied writes; and check current policy again before reading source bytes or publishing a result. K4-1 contains no collector, blob writer, authorization service, or end-to-end collector fence. Previously persisted blobs do not vanish when a grant changes. Revocation immediately stops ordinary metadata access and new persistence; a later deletion worker must remove or cryptographically discard raw and derived blobs, indexes, summaries, checkpoints, jobs, caches and projections, prevent stale regeneration, and report any incomplete cleanup. A timeline row alone is never deletion completion.

## Deliberate omissions and later seams

Migration 0163 adds **no `change_log` triggers or CDC coverage**. Comparative capture research and K5 CDC design still need to settle which policy and source metadata can be projected without leaking content. There is no sync writer, import/export implementation, provider upload, screen or AX collector, audio ingestion, permission UI, automatic observation, memory admission, loop/outcome creation, or projection table in this slice.

Later observation and episode projections may be keyed by stable observation/episode identity plus model version, tied back to source lineage and deletion generation. K4-3 may add embeddings only as subordinate, rebuildable, deletion-fenced projections, never a canonical source. A K5 sync design must preserve the portable IDs and daemon single-writer authority rather than re-keying source records.
